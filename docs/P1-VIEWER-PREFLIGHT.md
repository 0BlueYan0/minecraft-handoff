# P1 操作端隔離：下一個驗收關卡

## 要回答的問題

原啟動器正式啟動的常駐遊戲已可在保留既有驗證與連線時接入診斷代理。下一步要驗證完整 SAO 模組客戶端能否作為本機顯示端啟動、只連本機測試入口，而不另行登入真實 SAO 或改變常駐端的啟動 session。

這個階段還不複製常駐端的世界，不把一個獨立測試世界宣稱為接管成功。

## 目前已確認的輸入

- 本機 Minecraft 1.21.4 正式版本清單有 113 個 library 宣告、assetIndex 19、官方 server 下載項目。
- Fabric Loader 0.20.1 清單繼承 1.21.4，主類別是 KnotClient，另有 8 個 library 宣告。
- assets、libraries、loader/libraries、Java runtime 目錄均存在。
- 0.1.2 在目前常駐遊戲內只有觀察性回呼，沒有操作端入口、連線目的地導向或世界同步。
- 結構圖工具此時 Transport closed；上述確認來自直接讀取指定的版本 metadata 與 agent 入口，不宣稱做過完整結構圖探索。

## 最小實驗設計

1. 保留目前正常登入 SAO 的原遊戲，不重新登入、不更換其 PID。
2. 準備獨立 viewer 工作目錄。啟動所需版本、程式庫與資源可使用現有合法安裝作為輸入，但不複製 token、啟動器帳號資料、瀏覽器登入資料或原遊戲的存檔／快取。
3. Viewer 不呼叫第二次 Triggers 正式啟動流程。以本機測試身分執行，只代表本地顯示端，不代表另一個真正的 SAO 玩家登入。
4. 在本機 loopback 上啟動獨立測試伺服器；它不是接力伺服器，也不包含真實 SAO 世界。
5. Viewer 必須有可測試、預設拒絕的 Minecraft 連線目的地限制，只允許本次測試的 loopback 埠。限制就緒之前，不對使用者交付可直接連線的 viewer。
6. 驗證原 SAO 模組可載入、顯示本機測試世界，並觀察常駐端的原 PID、連線事件與驗證結果是否維持。

額外待查：SAO 模組可能另行呼叫官方 HTTP／WebSocket 服務。Minecraft 連線目的地限制不等於攔截所有這類服務；測試不得依賴轉送常駐端的驗證值來讓它們通過。

## 通過條件

- 兩個 Minecraft 程序可同時存在，viewer 的設定、日誌與可寫入資料均隔離。
- 只有原常駐端連著真正 SAO；viewer 的遊戲連線只到本機指定入口，連到其他位址的測試被拒絕。
- Viewer 可載入所需模組並進入本機世界；若有模組強制依賴官方啟動驗證，記錄為未通過，不偽造驗證成功。
- 常駐端原 PID 不變、沒有附加的重登、沒有新增斷線／Invalid token；明確記錄觀察時段。

## 後續順序

隔離實驗通過後，先在本機測試伺服器完成常駐端世界快照／增量到 viewer 的重建，再接上唯一控制權與基本操作轉交。原版流程可靠後，才逐項處理 SAO 任務、技能、隊伍與自訂 UI 狀態。
