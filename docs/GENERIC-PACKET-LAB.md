# 通用封包轉送：實驗與架構結論

日期：2026-11-11，Asia/Taipei。這份記錄是私有測試環境的可行性驗證，不是 SAO 相容性或 Mac 驗收報告。

## 已驗證的範圍

Windows Java21 / Minecraft1.21.4 / Fabric0.20.1。獨立 Fabric 後端只聽 127.0.0.1:25587；原本 Host 連到該後端，操作端連私人 frontend。只有後端與操作端安裝測試模組，Host 刻意沒有安裝它，也沒有該 payload 的 codec。測試角色全為自建本機假身分，沒有使用官方登入 token。

測試模組使用 `unfamiliar_test_mod:opaque_v9`。relay 原始碼沒有引用這個頻道或測試模組的任何類別；它只處理外層 framing、控制權和通用的連線頻道排除。S2C 在解碼之前擷取，避免 Host 將不認識的 payload 轉為 DiscardedPayload 後遺失內容。

| 驗證 | 實際結果 | 能支持的結論 |
|---|---|---|
| 操作端 → 原 Host transport → Fabric 後端 → 操作端 | 後端與操作端都取得 `0001ff007f802a`，內容相同 | 小型未知模組 payload 可經通用路徑雙向轉送 |
| 操作端執行原版 startAttack | `NATIVE_ATTACK_SWINGING=true` | 保留正常遊戲流程可以保留本機揮手；這項測的是原生方法，不是桌面實體按鍵 |
| 修正後路徑執行原生挖掘 | 後端放置 stone，原生攻擊後 RCON 驗證該位置為 air，`Test passed`；同時 swinging=true | 挖掘確實改變後端世界，沒有新增挖掘動作轉接 |
| 操作端 B 原生走路 | 後端 Pos 從 `(1.5,-60,-8.5)` 移動至約 `(1.505,-60,-4.402)` | 一般移動封包也能經通用路徑送達，沒有新增 walk 動作轉接 |
| 操作端 A → B | A 變 SPECTATOR，B 變 CONTROLLER；A 的後續測試不新增後端 echo，B 的測試新增一筆 | 這項實機測到操作端本機阻擋與 B 可送出；真正送出的過期 epoch 拒絕另由 ControlLeaseTest 驗證，不能混為同一項 |
| 多個本機 Minecraft 程序 | 後端 list 仍只有 HandoffHost 一名玩家 | 操作端加入沒有產生第二次後端玩家登入 |

此路徑目前只用於帶明確旗標且有 owned-fixture marker 的測試實例。C2S envelope 上限16,000 bytes；簽章聊天、所有連線狀態切換及所有模組語意尚未涵蓋，不能稱為任意封包大小／任意模組皆已通過。

## 中途加入：有成功案例，也有確定反例

Host 先收到完整狀態 `STATE|37`，操作端之後才啟動。新操作端透過有界 journal 重播，得到 `state=37`。第二個全新操作端 B 也取得37，證明這種「包含完整值的設定訊息」可以復原。

但是以下兩項失敗；它們是架構實驗的結果，不是把測試放寬成通過：

1. **已過期效果被重新啟動。** 後端約19:08:10送出 `EFFECT|10000`，語意為「接收後存在十秒」。操作端19:08:50才開始連線、19:08:54完成。第一次讀值仍為 `effectActive=true`。效果在原本時間線早已到期，重播卻把它當成剛發生的新事件。
2. **本機狀態無法憑空復原。** A 將測試模組的純本機欄位改成5，沒有送出任何封包。新 B 的該欄位仍為0。網路 journal 裡沒有這個資訊，因此單靠轉送不能取得它。

B 加入時也重播了 A 先前收到的 echo，還沒自己送請求就已有 `echoes=1`。這再次顯示「歷史事件全部重演」與「恢復現在狀態」是兩種不同操作。

## 審查修正與驗證

- 一般 C2S packet 解碼後，拒絕任何多餘尾端 bytes，避免把本地已能判定無效的資料送往原連線。native Swing codec 正常／追加垃圾的回歸測試通過。
- 實驗 S2C 改由單一 raw-frame 路徑傳送所有遊戲 frames，包含 bundle delimiters；停用同時存在的 decoded mirroring，避免 custom payload 插隊或重複。
- `OrderedWireMirrorTest` 驗證 delimiter → A → opaque B → C → delimiter 的順序與一次性，以及驗證／保活排除。這是單元測試，不能寫成原生 bundle 全情境已實機驗收。
- journal 限8192 frames / 8MiB；超出後拒絕 catch-up，不把截斷歷史當完整快照。
- 相關模組測試：relay-core22、relay-bridge6、viewer-bootstrap9全部通過；TLS sidecar先前3項測試也通過。建置記錄在本次工作目錄 `work/generic-review-green.log`，51秒成功。
- 修正後另以新 Host36148 / frontend3893 / 全新操作端75068重跑：加入前 `STATE|88` 成功恢復，未知 payload echo 原樣往返，原生攻擊將後端 `(2,-61,-5)` 的 stone 挖成 air。整段該次連線仍只有一名後端玩家。舊的37／TTL／A→B結果來自先前獨立測試階段，沒有把重啟前後算成同一段不中斷連線。
- 獨立審查的兩項實質問題已修正並複查通過；這不代替 Mac 或 SAO 實測。

## 架構判斷

採用「正常原生操作端＋通用封包轉送」作為後續方向，保留獨立的帳號／連線協調層；停止擴充逐項聊天、挖掘、技能的動作白名單。

中途接力需要**現在狀態的快照或重新同步**。可以先支援通用的 Minecraft 世界／玩家資料與有公開同步介面的模組狀態；SAO 另需查明其初始化、重新請求狀態和本機資料模型。對 SAO 所需的處理應集中在「加入時取得完整狀態」，而不是為每個技能重寫操作。

純本機、短暫的選單和動畫可以在加入時重新建立，但若該資料會影響實際技能／任務／裝備操作，就必須可靠同步，否則應拒絕接管。從 wire bytes 本身不能自動推斷任意模組的所有狀態語意。

Mac 常駐端／Windows 操作端啟動腳本草稿保留；最終 runtime 包仍待這項狀態同步方案、SAO 實服與 Mac 實機驗收。這次不將實驗程式包裝成已完成的 SAO 接力成品。
